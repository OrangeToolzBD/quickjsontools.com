JWT Decoder

A JWT decode splits the token at its two dots and Base64URL-decodes the first two parts, the header and the payload, which are both JSON. This decoder does that in your browser, shows the algorithm, issued-at and expiry times, and never sends the token anywhere. It does not verify the signature. Format per RFC 7519 (May 2015).

Updated September 20, 2026 · By Quick JSON Tools

How do I decode a JWT?

Paste the token into the box and press Decode. The tool checks that the token has exactly three dot-separated parts, decodes the header and payload, and shows both as formatted JSON. Above them, it lists the algorithm from the header, the expiry time from exp and the issued-at time from iat, as UTC dates.

The worked example from the tool’s tests uses this sample token (its signature part is a placeholder, not a real signature):

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjMiLCJuYW1lIjoiQW5hIiwiaWF0IjoxNzAwMDAwMDAwLCJleHAiOjE4MDAwMDAwMDB9.sig

It decodes to:

Header:  {"alg": "HS256", "typ": "JWT"}
Payload: {"sub": "123", "name": "Ana", "iat": 1700000000, "exp": 1800000000}
Issued:  2023-11-14T22:13:20.000Z
Expires: 2027-01-15T08:00:00.000Z

The expiry label compares exp with your computer’s clock and adds “(expired)” once that time has passed. If the payload has no exp or iat claim, the tool says so. Common errors and what they mean:

  • “A JWT has 3 parts separated by dots; this has 2.” The text was cut off, or it is not a JWT. Copy the whole token, including the part after the last dot.
  • “this has 5.” That is an encrypted token (JWE). Its payload cannot be read without the decryption key, so this tool rejects it.
  • “Could not decode” usually means stray characters, such as a Bearer prefix or quotation marks copied with the token. Remove them and try again.

What is inside a JSON Web Token?

A signed JWT has three Base64URL parts joined by dots: a header naming the signing algorithm, a payload of claims, and a signature over the first two. The header and payload are only encoded, not encrypted, so anyone holding the token can read them.

RFC 7515 (May 2015) defines this compact form, and RFC 7519 registers the standard claim names:

ClaimMeaning
issIssuer: who created the token
subSubject: whom the token is about, often a user ID
audAudience: the recipients it is meant for
expExpiration time: must not be accepted after this
nbfNot before: must not be accepted before this
iatIssued at: when it was created
jtiJWT ID: a unique identifier for the token

Times are NumericDate values: seconds since 1970-01-01T00:00:00Z, ignoring leap seconds. They are seconds, not milliseconds, which is a common bug when JavaScript code compares them with Date.now(). To turn any of these values into a date, use the Unix timestamp converter.

In the header, alg names the algorithm, typ is usually “JWT”, and kid hints at which key signed the token. Base64URL is the URL-safe Base64 alphabet without padding; the Base64 decoder accepts it too.

Is decoding a JWT the same as verifying it?

No. Decoding only reads the header and payload, which anyone can do. Verifying checks the signature with the right key and algorithm, and then checks claims such as exp and aud. Only a verified token can be trusted. This tool decodes; it never tells you a signature is valid.

Anyone can make a token that decodes to any claims they like, for example "role": "admin". The signature is what proves the issuer produced it. RFC 8725, the JWT best-practice document (2020), describes the attack in which a token’s alg is switched to “none” and a careless library accepts it without any signature check. It says libraries must let the caller fix the set of accepted algorithms.

On your server, verification should:

  • Use a maintained JWT library and pass an explicit list of allowed algorithms.
  • Reject “none” unless you deliberately rely on other protection.
  • Check that the key belongs to the expected issuer, and check aud when present.
  • Check exp and nbf, allowing only a small clock skew.

Never paste a live production token into any website, including this one. A valid token is a credential: whoever holds it can act as the user until it expires. This page keeps the token in your browser, but screenshots, clipboard history and browser extensions can still leak it. Use expired or test tokens where you can.

How do I decode a JWT in JavaScript?

In the browser or Node.js, take the second part of the token, convert Base64URL to standard Base64, decode it to bytes, read the bytes as UTF-8 and parse the JSON. That takes a few lines and no library, but it gives you unverified claims only.

function decodeJwtPart(part) {
  const b64 = part.replace(/-/g, "+").replace(/_/g, "/")
    + "===".slice((part.length + 3) % 4);
  const bytes = Uint8Array.from(atob(b64), c => c.charCodeAt(0));
  return JSON.parse(new TextDecoder().decode(bytes));
}
const [h, p] = token.split(".");
const header = decodeJwtPart(h);
const payload = decodeJwtPart(p);   // NOT verified

This mirrors what the tool does. The TextDecoder step matters: MDN notes (updated June 24, 2025) that atob returns a binary string, one character per byte, so names with accents come out garbled without it.

Reading claims on the client is fine for display, such as showing a user’s name or when a session ends. Access decisions belong on the server, after the library has verified the signature. In Node.js, use your JWT library’s verify function with the key and an explicit algorithm list rather than a decode-only helper.

Frequently asked questions

How do I decode a JWT token?

Paste it into the decoder above and press Decode. You will see the header, the payload and the issued and expiry times. To do it by hand, split the token at the dots and Base64URL-decode the first two parts; each is a JSON object. Remember that this shows the claims without proving they are genuine.

Is JWT decode safe?

Decoding itself is harmless, because it only reads data the token already exposes. The risk is where you paste it. This page decodes in your browser and sends nothing, but a live token is a credential, so avoid pasting production tokens into any site, and never treat decoded claims as trusted without verifying the signature.

Can I decode a JWT without the secret key?

Yes. The header and payload of a signed JWT are Base64URL-encoded, not encrypted, so they can be read without any key. The key is needed only to verify the signature, or to decrypt an encrypted JWT (JWE), which has five parts instead of three. Do not put secrets in a signed token’s payload.

How can I decode a JWT in Python?

With the PyJWT library, jwt.decode(token, key, algorithms=["HS256"]) verifies and decodes in one step. To read claims without verifying, pass options={"verify_signature": False}; the PyJWT documentation warns that the claims then cannot be trusted. jwt.get_unverified_header(token) reads the header, for example to find the kid.
