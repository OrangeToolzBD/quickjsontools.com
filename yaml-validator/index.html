YAML Validator

A YAML validator parses your YAML and reports the line and column of the first syntax error, or shows the parsed data if the file is valid. This one uses the MIT-licensed js-yaml parser, which follows the YAML 1.2 specification (version 1.2.2, October 1, 2021), and runs in your browser.

Updated September 20, 2026 · By Quick JSON Tools

How do I validate a YAML file?

Paste the YAML and press Validate. If it parses, the tool says “Valid YAML” and shows the result as JSON. If not, you get a message such as “Invalid YAML at line 2, column 7: bad indentation of a mapping entry”. Fix that spot and validate again.

Reading the JSON output is the real check. It shows exactly what a program will receive, so you can see whether a value became a string, a number, a boolean or null, and whether items landed under the parent you intended.

name: app
port: 8080
debug: false
zip: "02134"

{"name": "app", "port": 8080, "debug": false, "zip": "02134"}

Things this validator does and does not do:

  • It checks YAML syntax, not whether the file suits a particular program. A configuration file can be valid YAML and still have a misspelled key.
  • It reads one document. A file with several documents separated by --- gives “expected a single document in the stream, but found more”; paste each document on its own.
  • Comments start with # and are dropped from the output. The specification requires whitespace before a trailing comment, which is why http://x.com/#frag stays part of the value.

To convert the result or write YAML from JSON, use the JSON to YAML converter.

What are common YAML indentation errors?

YAML uses indentation to show structure, so most errors are spacing mistakes: a line indented under a key that already has a value, sibling keys at different depths, list items out of line, or tab characters. The YAML specification forbids tabs for indentation because systems display them differently.

Inputjs-yaml error
name: app then port: 80line 2, column 7: bad indentation of a mapping entry
a list line indented with a tabtab characters must not be used in indentation
a: b: cline 1, column 5: bad indentation of a mapping entry
key: "unclosedunexpected end of the stream within a double quoted scalar

These messages come from js-yaml 4.1.1 on the inputs shown. How to avoid them:

  • Indent with spaces only, and set your editor to insert spaces for the Tab key.
  • Keep sibling keys at exactly the same indentation.
  • A key either has a value on its own line or children beneath it, not both.
  • Quote any value containing : or #, so a: "b: c".
  • List items under a key can sit at the key’s indentation or deeper, but all items in one list must line up.
# wrong: "port" is indented under a key that already has a value
name: app
  port: 80

# right
name: app
port: 80

The column in an error points where the parser noticed the problem, which may be the line after the real mistake.

Why do yes, no and on become booleans?

Because YAML 1.1 treated words such as yes, no, on and off as booleans, and parsers built on 1.1 still do. YAML 1.2’s core schema only recognizes true and false (in lowercase, capitalized or uppercase forms). This validator follows 1.2, so yes and no stay strings here, but other tools may disagree.

The YAML 1.1 boolean type (working draft, January 18, 2005) lists y, yes, true and on, in several capitalizations, as true, and n, no, false and off as false. The js-yaml changelog records that y, yes, n, no, on and off are no longer converted to booleans. The specification’s core schema also resolves null, Null, NULL, ~ and an empty value to null. Here is what this validator returns:

enabled: yes
country: no
switch: on
ok: True
nothing: ~
zip: 007

{"enabled": "yes", "country": "no", "switch": "on", "ok": true, "nothing": null, "zip": 7}

Two lessons. First, a file that works here can be read differently by a YAML 1.1 parser, where yes becomes true and a country code of no becomes false. Second, 1.2 still types numbers, so a ZIP code of 007 becomes 7.

The fix is the same in both cases: quote values that must stay strings, such as country: "no" and zip: "007", and use true and false for real booleans.

Frequently asked questions

How do I add a comment in YAML?

Start the comment with #. It can take a whole line or follow a value, but a trailing comment needs a space before the #. YAML has no block-comment syntax, so comment out several lines by putting # at the start of each one.

Does this validator check Kubernetes or CI configuration files?

It checks that the file is valid YAML, which catches indentation and quoting mistakes, but it does not know any program’s schema. A misspelled key or a wrong value type will still pass. Use the target tool’s own validation for that.

Is JSON valid YAML?

Yes for YAML 1.2, which the specification defines as a strict superset of JSON. You can paste JSON here and it will validate, and the output will be the same data. For JSON-specific error messages, use the JSON validator instead.
