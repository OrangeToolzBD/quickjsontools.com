Unix Timestamp Converter

A Unix timestamp converter turns seconds since 00:00:00 UTC on January 1, 1970 into a date, and dates back into timestamps. For example, 1700000000 is 2023-11-14T22:13:20Z. The tool also reads milliseconds and microseconds. Under POSIX.1-2024, every day counts as exactly 86,400 seconds, so leap seconds are ignored.

Updated September 20, 2026 · By Quick JSON Tools

How do I convert a Unix timestamp to a date?

Paste the number and press Timestamp → date. The tool tells you whether it read the value as seconds, milliseconds or microseconds, then shows the date in UTC (ISO 8601), the same moment in your computer’s time zone, and the value in both seconds and milliseconds.

Worked example from the tool’s tests:

Read as seconds
UTC:        2023-11-14T22:13:20.000Z
Seconds:    1700000000
Millis:     1700000000000

Entering 1700000000000 gives the same date, read as milliseconds. To go the other way, type a date such as 2023-11-14T22:13:20Z and press Date → timestamp; the result is 1700000000. Include Z or an offset such as +02:00. In JavaScript, which this tool uses, a date and time without one is read in your local time zone. Press Now for the current timestamp.

// JavaScript
new Date(1700000000 * 1000).toISOString()   // "2023-11-14T22:13:20.000Z"
Math.floor(Date.now() / 1000)                // now, in seconds

# Python
from datetime import datetime, timezone
datetime.fromtimestamp(1700000000, tz=timezone.utc)

# GNU date
date -u -d @1700000000

JWT exp and iat claims are Unix seconds; the JWT decoder converts them for you.

Seconds or milliseconds: how can I tell?

Count the digits. A present-day timestamp has 10 digits in seconds, 13 in milliseconds and 16 in microseconds. This tool applies the same idea: values of 100 billion (10¹¹) or more are read as milliseconds, and values of 100 trillion (10¹⁴) or more as microseconds.

ValueRead asDate (UTC)
1700000000seconds2023-11-14 22:13:20
1700000000000milliseconds2023-11-14 22:13:20
1700000000000000microseconds2023-11-14 22:13:20

The cut-off works because 10¹¹ seconds would be in the year 5138, far beyond any date you are likely to store. The one blind spot is the other end: 10¹¹ milliseconds is March 3, 1973, so a millisecond value for a date before then is read as seconds. Check the “Read as” line when handling old dates.

Languages differ in their defaults. MDN (updated December 8, 2025) confirms that JavaScript’s Date.now() returns milliseconds, while POSIX time and JWT claims count in seconds. Mixing them up gives dates in 1970 or tens of thousands of years ahead.

What is the year 2038 problem?

Systems that store Unix time in a signed 32-bit integer run out at 2,147,483,647 seconds, which is 03:14:07 UTC on January 19, 2038. One second later the counter overflows to −2,147,483,648, which such a system reads as 20:45:52 UTC on December 13, 1901. Moving to 64-bit time values removes the limit.

Both dates are exact calculations from the timestamp definition, and you can confirm them in this tool by entering 2147483647 and -2147483648.

Where to look for the problem in your own work:

  • Database columns, file formats and network protocols that store time in 32 bits.
  • Older embedded devices and C code built with a 32-bit time_t.
  • Anything that computes dates in the future, such as certificate expiry or 20-year schedules, which can fail before 2038 arrives.

JavaScript is not affected: MDN gives the Date range as ±8,640,000,000,000,000 milliseconds, about 100 million days either side of 1970. Version 7 UUIDs are safe too, since they store 48 bits of milliseconds; the UUID generator explains the layout.

Frequently asked questions

What is the current Unix timestamp?

Press Now in the converter. It shows the current time in seconds and milliseconds along with the UTC date, taken from your computer’s clock, so it is only as accurate as that clock. In code, Math.floor(Date.now() / 1000) gives the same value in seconds in JavaScript.

Does Unix time count leap seconds?

No. POSIX defines every day as exactly 86,400 seconds, so leap seconds are not counted, and a Unix timestamp is not a true count of the seconds elapsed since 1970. JavaScript dates follow the same rule, which keeps date arithmetic simple at the cost of that small difference.

Does a Unix timestamp depend on the time zone?

No. A timestamp identifies one instant, the same everywhere on Earth. Time zones only affect how that instant is displayed, which is why the converter shows both UTC and your local time for the same value. Store timestamps or UTC dates, and convert to local time only for display.
